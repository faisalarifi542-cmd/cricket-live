7. PROVIDER TIMEOUT / RETRY POLICY  (review)
================================================================================
  Provider abstraction: providers/ base-provider + provider-manager (execute()),
  multi-provider failover (cricbuzz/cricinfo/cricketdata). Cricbuzz parses JSON
  from HTML — FRAGILE by nature.
  RECOMMENDATION [DOC]:
    - Per-provider HTTP timeout 4-6s; fail fast to next provider rather than
      hanging a request under load.
    - Retry: at most 1 retry on a provider before failover (avoid retry storms
      amplifying load when a provider is down).
    - Cache last-good payload; on total provider failure serve stale + flag
      isStale:true (rankings already returns clean-empty on failure — extend the
      stale-serve pattern to match list/live where safe).
    - Add parser regression tests (M6 in review) so provider HTML changes are
      caught in CI, not in prod.

8. PM2 CLUSTER MODE  [VPS manual — no ecosystem.config.js in repo]
================================================================================
  SUGGESTED ecosystem.config.js (create on server, do NOT commit secrets):
    module.exports = { apps: [{
      name: 'cricket-api',
      script: 'src/server.js',
      instances: 'max',        // or a fixed number = CPU cores
      exec_mode: 'cluster',    // load-balance across cores
      max_memory_restart: '500M',
      env: { NODE_ENV: 'production' },
    }]};
  CAUTION: cluster mode requires the app be stateless across instances. This app's
  Redis cache is shared (good), but the in-memory fallback cache is PER-INSTANCE —
  under cluster mode, ensure Redis is UP so all workers share cache (otherwise each
  worker caches separately = more provider hits). Verify before enabling 'max'.
  See SERVER_HIGH_TRAFFIC_CHECKLIST.txt §1.
