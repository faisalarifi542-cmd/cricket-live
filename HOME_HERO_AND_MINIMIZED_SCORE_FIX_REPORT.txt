2. WHY CAROUSEL SLIDES/JUMPS ON SCORE UPDATE  (BUG 1 — ROOT CAUSE)
--------------------------------------------------------------------------------
The carousel controller/index are stable. The jump comes from the DATA changing
ORDER/IDENTITY beneath a position-based (modulo) PageView:

ROOT CAUSE A (primary): _refreshHeroSilently (home_screen.dart:758) calls
  _resolveHero(forceRefresh:true) on every membership tick. _resolveHero re-runs
  _prioritiseHero (:311) + (on fallback) _loadHero aggregation (:488). This can
  REORDER the hero list (favourite float, live-first sort, dedup order). The
  PageView maps the CURRENT page number through `index % items.length`; if the
  list order changes, the SAME page number now points to a DIFFERENT match — the
  visible card appears to slide/jump even though _controller never moved.

ROOT CAUSE B: even when content is identical, _refreshHeroSilently swaps in a brand
  new `Future.value(freshHero)` (:790). FutureBuilder rebuilds; because items carry
  NO id-based Key, Flutter reuses element slots positionally. With looping
  (itemCount = items.length*2000, initialPage = length*1000) any change in
  items.length shifts every realIndex -> jump.

ROOT CAUSE C: _overlayFastLiveScores (:808) also reassigns _heroFuture every tick
  when score changed (:888). It preserves ORDER (maps over existing _heroData), so
  it is safe for order, but still rebuilds FutureBuilder; combined with no keys it
  can still cause the AnimatedBuilder scale/opacity transform to re-fire a frame.

Net: score updates funnel through full hero-list reassignment + reorder, and the
modulo PageView has no stable per-match key to hold position by identity.

5. WHY MINIMIZED SCORE DOES NOT UPDATE  (BUG 3 — ROOT CAUSE)
--------------------------------------------------------------------------------
- `update()` is called from ONE place: the MatchDetails silent poll
  (match_details_screen.dart:370). That poll's Timer is owned by
  _MatchDetailsScreenState and is CANCELLED on dispose (when the user leaves match
  details / minimizes + pops).
- So once minimized, NOTHING polls fresh data for the bar. The Home poll
  (_silentPoll / _overlayFastLiveScores) NEVER touches MinimizedScoreController.
- Result: bar shows the frozen snapshot captured at show() time.
- RootShell (_RootShellState main.dart:270) is a plain State with NO lifecycle
  observer and NO timer — there is no existing app-shell polling to piggyback on.
- CricProApp (main.dart:64) HAS WidgetsBindingObserver — usable reference, but the
  cleanest fix is a small self-contained poller inside the controller.

7. SAFE FIX PLAN
--------------------------------------------------------------------------------
PHASE 2 — Carousel stability (BUG 1):
  a) Give each PageView item a STABLE id-based key (ValueKey(match.id)) so Flutter
     holds element identity by match, not slot position.
  b) Track the currently-visible match BY ID in _HeroMatchCarousel. On didUpdateWidget
     (new items), if the previously-visible matchId still exists, KEEP showing it:
     if its index changed, silently re-seat the controller to that match's page
     WITHOUT animation (jumpTo via controller, no animateToPage). If the matchId is
     gone, clamp to nearest valid index.
  c) Stop _refreshHeroSilently from REORDERING on silent polls: preserve previous
     hero order, overlay only score/status by id (same approach already used by
     _overlayFastLiveScores). Do NOT re-run _prioritiseHero on silent refresh —
     only on user refresh / initial load / membership change.
  d) Gate hero Future reassignment: only swap _heroFuture when the hero MEMBERSHIP
     (id set/order) changes; for pure score change, mutate the existing items in
     place keyed by id so the visible card updates text without list reset.

PHASE 3 — First-load split (BUG 2):
  a) Derive heroIds from the SAME data the list uses, as early as possible. Either:
     (i) hold list rendering behind a combined "first snapshot ready" gate showing
     skeletons, OR (ii) compute a provisional primary hero id synchronously from the
     first available match data so excludeIds is non-empty on first list paint.
  b) Ensure list filter always excludes the resolved primary hero id; never render a
     hero-selected match in the list. Keep skeletons during initial load (already
     present, home_match_cards.dart:181, home_hero.dart:45).
  c) Do not block hero/list placement on logo/feed enrichment — decide placement from
     match ids immediately, enrich visuals after.

PHASE 4 — Minimized live update (BUG 3):
  a) Add a private poller to MinimizedScoreController: when show(match) and match
     isLive, start Timer.periodic(~5s) -> repository.liveScores([id]) -> if fresh
     score key differs, update() (merge) + notify. Reuses in-flight backend cache;
     liveScores already de-duped server-side (~4s).
  b) Stop the timer on: clear(), match no longer live (isFinished/terminal), and app
     background. Resume on foreground if still live. Hook lifecycle via a lightweight
     WidgetsBindingObserver inside the controller (registered on first show, removed
     when idle) OR via CricProApp's existing observer (main.dart:108).
  c) On fetch failure: keep last good score, no error UI in the compact bar.
  d) Rebuild ONLY the bar (already isolated via AnimatedBuilder main.dart:568).
  e) If MatchDetails is open for the same match, its poll still calls update() — the
     controller's own poll and that path both funnel through update() (same-id guard),
     no duplication of visible state. To avoid double network calls, the controller
     poll can skip a tick if a recent update() arrived (track lastUpdate time).
